# 故障恢复与服务交接

从实际请求、服务日志和运行身份开始。健康接口正常、无流量、队列阻塞、模型数值异常、设备故障和观察器失联是不同现象。先保存复现请求与首错，按假设选择 replay、trace、dump 或多 rank 调试，避免所有故障都先抓大 trace。

## 多节点和恢复

冻结全部必需服务 member、节点/容器/PID namespace、launch/attempt、进程启动时间与设备。rank0 能响应不能证明其余 rank 健康；完整退出需核全部 launcher、首错、日志封存与服务契约。检查遥测新鲜度和采集器自身心跳，控制节点在线不代表服务容器在线。

只由既定 `recovery_owner` 管理恢复。SSH 超时、控制器异常、租约过期都不能证明远端退出；先 reconcile 原 operation。用精确身份停止任务进程，不按模糊名称清理其他服务。已知失败、未知结果、完成但证据未采回分别处理；未知状态期间不并发启动替代操作。

恢复后重新核模型/权重身份、实际 endpoint、rank 组、warmup、固定请求、质量和必要 KV/会话恢复行为。重新加载权重不等于恢复进行中的会话；重试请求须遵守请求幂等与缓存契约。故障注入限已授权隔离范围，不能在生产上默认制造掉卡或断网。

## context 与观察交接

拓扑扩容与配方验收交部署 Skill，性能取舍交模型优化 Skill；扩容导致的故障由本 Skill 定位。新拓扑的证据不可复用旧 context 的 pass，具体范围见工程 `docs/operations.md`。

保留旧 Store/日志/manifest/事件游标。源码、模型、拓扑或 workload 改变时创建或更新任务 context 并重新绑定证据；相同 context 的普通重启用新 attempt。观察器从同一固定版本部署，先单次检查再确认所有必需成员 ready 和心跳。事件导出游标必须属于相应 Store，不能拿旧库 seq 消费新库。通知投递、Agent 消费和恢复成功分别保留回执。

持续守护需要站点的实际采集和监督机制，本仓 `observe` 是规范化样本入口，`flow-watch` 也不等于服务守护。交付写明观察覆盖、实际运行时间、漏测的长稳/恢复条件和接管负责人。
